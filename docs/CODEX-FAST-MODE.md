# Codex fast 모드 집계 검토

검토·구현일: 2026-11-16. 아래에는 조사 근거와 확장 설계를 함께 기록합니다.

## 구현 상태

- 모델명을 유지하면서 선택/요청 등급을 `UsageEvent.service_tier`에 저장합니다. `priority`/`fast`는 `fast`, `standard`/`default`는 `default`, 누락은 빈 값으로 정규화합니다. `auto`와 기타 등급은 별도로 유지합니다.
- Codex의 설정 스냅샷과 필드가 존재하는 턴 컨텍스트를 읽습니다. 등급 없는 새 스냅샷은 이전 Fast를 이어받지 않으며, 타 스레드 소유가 명시된 스냅샷은 무시합니다.
- SQLite/PostgreSQL 마이그레이션과 미상 등급의 보완 갱신을 추가했습니다. 이전 Codex 커서는 한 번 재스캔하며 이벤트 ID를 바꾸지 않습니다.
- 사용량 조회 전체에 `service_tier` 필터, breakdown/timeseries/throughput에 등급별 그룹을 추가했습니다. 누락 등급의 그룹 키는 `unknown`입니다. 다른 수집기의 등급 없는 이벤트도 미상 필터에 포함됩니다.
- 모델 화면에 Codex 등급별 토큰·비중·이벤트·환산 비용 표와 등급 필터, 이벤트 화면에 필터와 배지를 추가했습니다. 기존 모델별 합계는 유지합니다.
- 비용은 **Standard API 단가 기준 환산**으로 유지합니다. 아래의 등급별 단가 설계는 후속 확장 사항입니다.

서버를 먼저 업데이트한 뒤 에이전트를 업데이트해야 이전 로그의 등급 보완을 받을 수 있습니다. 이미 에이전트를 먼저 업데이트했다면 서버 업데이트 후 재동기화를 요청하면 됩니다.

## 결론

fast 모드를 선택한 사용량은 로그에 서비스 등급이 남아 있으면 구분해 집계할 수 있습니다. 구현 전 코드는 이 정보를 버려 일반 모드와 합쳤습니다.

모델명은 원본 그대로 유지하고 서비스 등급을 별도 차원으로 추가하는 방안을 권장합니다. 화면에서는 같은 모델 아래 `Standard`, `Fast`, `알 수 없음`으로 나눠 보여주면 됩니다. 로그에서 확인한 설정과 실제 서버가 처리·과금한 등급은 구분해야 합니다.

## 확인한 근거

### 구현 전 프로젝트 코드

- `internal/collector/codex/codex.go`: `turn_context`와 `thread_settings_applied`에서 모델만 읽습니다. 커서의 `fileState`에도 서비스 등급이 없습니다.
- `internal/event/event.go`: 공통 `UsageEvent`에 등급 필드가 없습니다.
- `internal/store/migrations/{sqlite,postgres}/0001_init.sql`: `usage_events`에 등급 컬럼이 없습니다.
- `internal/store/query.go`: 비용 계산 전 집계는 모델·소스·UTC 날짜·시간 버킷·긴 컨텍스트 구간으로 나누며 서비스 등급은 구분하지 않습니다.
- `internal/pricing/pricing.go`: 단가 선택 기준은 모델과 시각입니다.
- `internal/store/events.go`: 같은 이벤트를 다시 보내도 출력 토큰 증가 또는 미상 모델 보완 이외에는 갱신하지 않습니다.

### 실제 로컬 로그 표본

로컬 `~/.codex/sessions`에서 수정 시각이 최근인 비압축 JSONL 80개를 읽고 설정 메타데이터만 확인했습니다. 표본에는 CLI 0.166.0, 0.167.0, 0.167.1, 0.167.2, 0.169.0의 세션 메타데이터가 있었습니다. 모든 버전에서 동일하게 기록된다는 의미는 아닙니다.

| 위치 | 관찰 결과 |
|---|---|
| `turn_context.payload.service_tier` | 확인한 547개 레코드 모두 필드 없음 |
| `event_msg.payload.thread_settings.service_tier` (`type=thread_settings_applied`) | 527개 중 `default` 125개, `priority` 2개, 필드 없음 400개 |
| `token_count.payload.info` | 확인한 표본에서 실제 처리 등급 필드를 찾지 못함 |

다음은 관찰한 필드만으로 재구성한 예시입니다. 원본 대화 내용은 포함하지 않았습니다.

```json
{"type":"event_msg","payload":{"type":"thread_settings_applied","thread_settings":{"model":"gpt-6.1-sol","service_tier":"priority"}}}
```

같은 세션에서 모델은 `gpt-6.1-sol`로 유지하면서 `default`에서 `priority`로 바뀐 사례도 확인했습니다. 따라서 세션 전체를 하나의 등급으로 지정하면 전환 이전 사용량까지 잘못 분류할 수 있습니다. 각 사용량 레코드를 읽을 때 그 시점에 유효한 설정을 연결해야 합니다.

이 결과는 이 환경의 일부 파일에 대한 관찰입니다. 기록 형식과 필드 존재 여부는 클라이언트·버전에 따라 달라질 수 있습니다.

### 공식 자료와의 대조

[Codex 설정 문서](https://learn.chatgpt.com/docs/config-file/config-reference)는 `service_tier`를 새 턴의 선호 등급으로 설명하며 `fast`가 요청 값 `priority`에 대응한다고 명시합니다. 따라서 fast를 별도 모델로 저장할 이유가 없습니다.

[공식 프로토콜 소스](https://github.com/openai/codex/blob/main/codex-rs/protocol/src/protocol.rs)의 `ThreadSettingsSnapshot`에는 선택적 `service_tier`가 있고, `TokenUsageInfo`에는 실제 처리 등급 필드가 없습니다. [`ServiceTier` 정의](https://github.com/openai/codex/blob/main/codex-rs/protocol/src/config_types.rs)는 `fast`와 `priority`를 같은 등급으로 해석합니다. 이는 검토 시점의 main 소스이며 설치된 모든 버전의 계약은 아닙니다.

[API fast 문서](https://developers.openai.com/api/docs/guides/fast-mode)는 응답의 `service_tier`가 실제 처리 등급을 나타내며, fast 요청이 일반 처리로 내려갈 수도 있다고 설명합니다. 설정 로그만으로 실제 fast 처리·청구를 확정해서는 안 됩니다.

## 대안 비교

| 방안 | 장점 | 문제점 | 판단 |
|---|---|---|---|
| 모델명을 `gpt-6.1-sol-fast` 등으로 변경 | 기존 모델별 화면을 쉽게 재사용 | 원본 모델명 훼손, 모델 합계 분산, 별칭 단가 충돌, 과거 모델명 갱신 제약 | 비권장 |
| 모델과 서비스 등급을 별도로 저장 | 원본 유지, 모델 합계와 등급별 집계 모두 가능 | DB·전송·집계·UI 확장 필요 | 권장 |
| 세션별 태그 또는 현재 `config.toml`로 분류 | 구현이 단순 | 세션 중간 전환·과거 설정·자식 세션 차이를 반영하지 못함 | 보조 진단에만 사용 |
| 응답 시간으로 추정 | 설정 로그가 없어도 시도 가능 | 부하·도구 실행·출력량에 영향받아 신뢰할 수 없음 | 사용하지 않음 |

모델명 접미사 방식은 현재 `pricing.yaml`의 `gpt-6.1-sol*` 같은 별칭 규칙에 걸려 일반 단가로 계산될 수 있습니다. 기존 데이터의 모델은 `unknown`인 경우 외에는 재전송으로 바뀌지 않으므로 과거 데이터 보완에도 불리합니다.

## 권장 데이터와 표시 방식

최초 구현은 **선택한 등급별 토큰 집계**에 초점을 맞춥니다.

- `model`: 원본 모델명 유지.
- `requested_service_tier`: 로그의 선택값 보관. 값이 없으면 미상으로 둠.
- 표시·필터용 정규화: `default` → Standard, `priority`/`fast` → Fast. 그 외 값은 보존하고, 미지원 값을 Standard로 바꾸지 않음.
- 향후 실제 응답 등급을 수집할 수 있으면 `actual_service_tier`를 별도 추가. 설정값을 이 필드에 넣지 않음.

`fast: bool`만 두면 미상과 일반 모드를 구분하기 어렵고 다른 등급도 표현할 수 없습니다. 필드가 없거나 `auto`인 기록은 명시적 `default`와 구분해야 합니다.

기존 모델 합계는 유지하고, 모델 행을 펼치거나 선택적 `모델 × 등급` 보기로 세분화하는 구성이 적합합니다. 이벤트 목록에는 등급 배지, 전체 조회에는 등급 필터를 추가합니다. 미상 비율도 보여주면 분류 가능한 데이터 범위를 알 수 있습니다.

## 비용 계산

현재 프로젝트의 비용은 실제 청구액이 아니라 API 단가 환산액입니다. 다음 세 가지를 혼합하지 않아야 합니다.

1. 원본 토큰 수: fast라고 곱하지 않습니다.
2. API 환산 비용: 해당 모델·등급·날짜의 공개 API 단가를 적용합니다.
3. 구독 한도·크레딧 소모: 별도의 과금 체계입니다.

검토 시점 [Codex 속도 문서](https://learn.chatgpt.com/docs/agent-configuration/speed)는 지원 모델의 Fast에 대해 포함 구독 한도는 일반의 2.5배, 구매 크레딧과 Enterprise 종량제는 2배라고 설명합니다. 이 수치를 토큰 수나 모든 API 단가에 일괄 적용해서는 안 됩니다.

최초 단계에서는 기존 비용을 명확히 'Standard API 단가 기준 환산'으로 유지하면서 등급별 토큰을 제공할 수 있습니다. 등급별 환산을 추가할 때는 다음이 필요합니다.

- 단가 조회를 `(model, service_tier, timestamp)` 기준으로 확장하고 기간별 단가와 긴 컨텍스트 요금을 함께 처리.
- SQL 중간 집계에도 서비스 등급을 추가. 다른 단가의 토큰을 합친 다음 가격을 매기면 총비용이 틀려짐.
- 설정값만 사용한 등급별 비용에는 추정 표시. 실제 처리 등급을 확인한 것처럼 표시하지 않음.
- fast 단가가 없을 때는 비용 미상으로 처리하거나, 명시적으로 표시한 Standard 기준 환산을 제공. 일반 단가를 fast 단가로 조용히 대체하지 않음.
- 등급 미상·단가 미상과 토큰 수의 정확도는 별개로 표시.

## 구현 범위와 과거 이력

1. 수집기: 설정 이벤트를 읽고 파일별 커서에 등급 상태 저장. 중간 전환, 모델 전환, 압축 로그, 증분 읽기·재시작을 처리.
2. 상태 해석: 완전한 설정 스냅샷과 부분 변경을 구분. 새 스냅샷에서 등급이 생략됐는데 이전 Fast를 무조건 유지하지 않음. 버전별 생략·null 의미를 검증하고 불명확하면 미상으로 처리. 소유 스레드가 있는 기록은 다른 스레드의 설정을 잘못 적용하지 않도록 확인.
3. 이벤트·전송·저장: 공통 이벤트와 SQLite/PostgreSQL에 선택적 등급 필드 추가. 기존 에이전트의 누락값은 미상으로 호환.
4. 조회·UI: 등급 필터와 집계 차원, 배지, 미상 표시 추가. 모델 합계는 그대로 제공.
5. 이력 보완: 같은 이벤트 ID의 미상 등급을 알려진 값으로 보완하는 서버 갱신 규칙 추가. 기존 기기 소유권 검사 유지, 구버전 재전송으로 알려진 값을 지우지 않음.
6. 서버를 먼저 배포한 뒤 에이전트를 갱신하고 재수집. 등급 상태가 없던 기존 커서는 메타데이터 복원 또는 한 번의 재스캔 필요.

기존 `rescan`/`resync`만 실행하면 동일한 토큰 수의 이벤트는 중복으로 무시되므로, 서버의 메타데이터 보완 규칙이 먼저 필요합니다. 이벤트 ID의 계산 방식은 그대로 유지해야 합니다. ID를 바꾸면 같은 사용량이 새 이벤트로 들어갈 수 있습니다.

원본 로그에 등급이 없거나 세션 자체가 저장되지 않았다면 과거 fast 여부는 복원할 수 없습니다. 현재 설정 파일로 과거 기록을 소급 분류하지 않습니다.

구현 시 핵심 검증은 같은 모델의 Standard → Fast → Standard 전환, 설정 누락·null, 증분 재시작, 압축 로그 재수집, 기존 에이전트와의 혼용, 중복 없는 미상 등급 보완입니다. 등급별 비용을 추가하면 혼합 등급 합계와 기간별·긴 컨텍스트 단가의 조합도 검증해야 합니다.

현재 구현 범위는 위의 '구현 상태'를 참고하세요. 실제 처리 등급 수집, 등급별 API 단가 및 구독 한도·크레딧 소모 계산은 포함하지 않습니다.

## 구현 검증 결과

- `go vet ./...`, `go test -race ./...` 통과. DB 관련 실행 검증은 SQLite 기준이며 PostgreSQL 실DB 검사는 수행하지 않았습니다.
- 수집기에서 Standard → Fast → Standard 전환, 등급 누락·null, 타 스레드 스냅샷, 증분 재시작, 구버전 커서의 한 번 재스캔, 압축 로그의 이벤트 ID 유지 검증.
- 저장소에서 기존 DB 마이그레이션, 같은 토큰 수의 등급 보완, 기기 소유권, 구버전 재전송·출력 증가 시 등급 보존, 모든 조회의 등급 필터와 기존 모델·비용 합계 유지 검증.
- 웹 단위 테스트 98개, TypeScript 검사와 프로덕션 빌드 통과.
- 새 Playwright 시나리오가 데스크톱·모바일 × 라이트·다크 4개 환경에서 통과. 임시 SQLite 서버와 합성 이벤트로 모델 필터·추이·처리량 요청, 이벤트별 Standard/Fast/미상 필터와 배지를 검증했습니다.
